# FoodBridge — notes for Claude

Surplus-food donation platform (FoodWasteZero initiative, Dhaka). Donors post surplus food, NGOs request it, volunteers carry it, and admins verify partners.
Stack: Next.js 16 (App Router) · React 19 · TypeScript · Tailwind CSS v4 · Drizzle ORM on PGlite · jose JWT sessions · zod 4.
User-facing setup, seeded accounts and the business flow are in [README.md](README.md). This file covers what you need in order to change the code safely.

## Commands

```bash
npm run dev      # http://localhost:3000
npm run build    # also runs the TypeScript check
npm run lint     # eslint (next config)
npx tsc --noEmit # quick type check
```

There is no test suite. Verify changes with `npx tsc --noEmit`, `npx eslint src` and `npm run build`, then click through the flow in a browser.

**Only one process can open a PGlite folder.** `src/db/index.ts` takes a pid lock (`.data/pglite.lock`). If the user's dev server is running, start a second server against a throwaway database instead of stopping theirs:
`DATABASE_DIR=<scratch dir>/pg DEMO_MODE=true npx next start -p 3100` (after `npm run build`).
On Windows, stopping the `npx next start` wrapper can leave the Next server running; check the port (`Get-NetTCPConnection -LocalPort 3100`) and stop that node process.

Env (`.env.local`, see `.env.example`): `SESSION_SECRET` (32+ chars, required), `DATABASE_DIR`, `APP_TIMEZONE` (default `Asia/Dhaka`), `DEMO_MODE`, `ADMIN_EMAIL` / `ADMIN_PASSWORD`, `CRON_SECRET` (protects `/api/cron/housekeeping`). Optional: `GEMINI_API_KEY` / `OPENROUTER_API_KEY` / `ANTHROPIC_API_KEY` (assistant, tried in that order; models via `GEMINI_MODEL`, `OPENROUTER_MODEL`, `AI_MODEL`; without any key it runs in no-AI help mode), `NOTIFY_*_WEBHOOK_URL` (outside channels), `NEXT_PUBLIC_MAP_TILE_URL`, `INTEGRATION_SECRET` (+ `NEXT_PUBLIC_WHATSAPP_NUMBER`, `NEXT_PUBLIC_MESSENGER_PAGE`, `APP_URL`) for the n8n chat integration.

Service-level tests: there's no test runner, but services can be exercised with `DATABASE_DIR=<scratch> npx tsx --conditions=react-server <script>.ts` (the condition makes `server-only` importable). Scripts don’t read `.env.local` by themselves; add `--env-file=.env.local` and run them from inside the project so `node_modules` resolves.

Browser testing with the Playwright MCP: simulated mouse clicks on submit buttons are sometimes dropped (no request is sent), but the app itself is fine. Submit with a DOM click instead: `locator.evaluate(el => el.click())`. Wait for `networkidle` before filling a form.

## Next.js 16 specifics

- Route protection lives in `src/proxy.ts` (Next 16 renamed `middleware` to `proxy`). It only checks the cookie. The real check is the DAL.
- `params` and `searchParams` are Promises. Pages use the global `PageProps<"/route">` and route handlers use `RouteContext<"/route">` types (generated by `next build`/`next dev`).
- Check `node_modules/next/dist/docs/` or context7 before using an API you're unsure of. Don't rely on memory of Next 13–15.

### Invariants — keep these true

- **Every donation status change goes through `transitionDonation()` / `transitionInTx()`** in `src/lib/donations/service.ts`. `ALLOWED_FROM` is the only source of workflow rules. The conditional `UPDATE … WHERE status IN (…)` is what makes concurrent actions safe (for example two volunteers accepting the same task). The transition also writes `donation_events` and sends the donor, NGO and volunteer notices. Don't update `donations.status` directly.
- Workflow: `PENDING → MATCHED → ASSIGNED → PICKED_UP → IN_TRANSIT → DELIVERED → COMPLETED` (IN_TRANSIT is optional: DELIVERED is allowed from PICKED_UP too), plus `CANCELLED` (donor or admin, until pickup) and `EXPIRED` (from PENDING/MATCHED/ASSIGNED). The timeline labels the first (PENDING) event "Created".
  - MATCHED is reached only through `allocateInTx()` (`lib/matching/service.ts`): the donor accepts an NGO's direct request (`acceptRequest`), or the NGO/admin accepts a system match (`acceptMatch`). It locks the donation, transitions to MATCHED with the delivery snapshot (`delivery_address/lat/lng`, `deliver_by`), then splits off any surplus as a new PENDING donation (`parent_id`), marks the request ACCEPTED + `allocated_at`, logs ALLOCATED and calls `declineOtherRequests()`.
  - Special moves: `releaseVolunteer` (ASSIGNED → MATCHED; volunteer hands back or admin releases) and `unmatch` (MATCHED/ASSIGNED → PENDING; `cancelMatch()` by NGO or admin). Both re-offer/re-match automatically.
  - Dispatch (`lib/dispatch/service.ts`, called from `transitionInTx`): on MATCHED the task is offered to ONE volunteer at a time, nearest first (`task_offers`, UNIQUE per donation+volunteer). Decline or no answer in `DISPATCH_RULES.offerMinutes` → next volunteer; nobody left → open to all available volunteers. A task offered to someone else is hidden from others and can't be accepted by them.
  - `transitionInTx` refuses MATCHED and ASSIGNED once `expires_at` has passed, so expired food can never be committed even before the sweep marks it.
  - Admin-only options: `byAdmin` changes the cancellation notices to "FoodBridge cancelled…"; `releaseVolunteer` moves ASSIGNED → MATCHED, clears the volunteer and re-offers the task.
  - Volunteer accepts → ASSIGNED, confirms pickup → PICKED_UP, "Start delivery" → IN_TRANSIT, confirms delivery → DELIVERED. The NGO can also confirm DELIVERED.
  - The NGO enters meals served → COMPLETED.
- **Food safety** (`lib/safety/meta.ts` `SAFETY_RULES`): the donor's best-before (`expires_at`) is the single expiry for everything; `safetyWindowIssue()` caps it per category/condition at posting time. An admin hold (`safety_flag` FLAGGED) removes food from matching, the available list and requests, and `transitionInTx` refuses MATCHED/ASSIGNED while any `safety_flag` is set. DISABLED = cancelled as unsafe. Expiry warnings go out once per donation+user (`sendExpiryWarnings`, housekeeping).
- **Notifications**: always call `notify()` / `notifyAdmins()` from `lib/notifications/service.ts` (donations/service re-exports `notify`); pass `{ requestId, needId }` links when relevant. Every new `NotificationType` needs `STYLE` (notifications-view.tsx) **and** `NOTIFICATION_CATEGORY` (notifications/meta.ts); both are `Record`s. A DB trigger queues `notification_deliveries` for users' opted-in channels; `flushOutbox()` sends only `EXTERNAL_CATEGORIES` through `CHANNELS` adapters. Workflows never talk to channels directly.
- **Assistant chats** (`ai_conversations` + `ai_messages.conversation_id`): titled from the first message (`titleFrom`), listed in the full-screen `/assistant` sidebar, scoped to the user in every query (`lib/ai/history.ts`). The floating panel continues the latest chat; its full-screen button passes `?c=` and `?from=` (Back only accepts same-site paths).
- **Reports & exports** (`lib/reports`): one set of aggregate queries over donations (filters: date posted, location, donor type, status, NGO) feeds `/admin/reports`, `/ngo/reports` and CSV. Exports are admin-only, logged as `data_export`, and never include emails, phones, home addresses, coordinates, photos or password hashes; `toCsv` neutralises spreadsheet formulas. Dashboards' "over time" cards use `lib/analytics` (deliveries counted at the DELIVERED event, in the app timezone).
- **Chat integration** (`lib/integrations`, `POST /api/integrations/inbound`, Bearer `INTEGRATION_SECRET`): n8n forwards messages, we answer `{ reply }`. Accounts are linked with a one-time code (hashed, 15 min). DONATE/NEED drafts are validated with the same zod schemas as the web forms and created only after YES (`pending_draft`). Chat apps receive only `CHAT_CATEGORIES` updates, addressed to the linked id. The website stays the source of truth; see `integrations/n8n/README.md`.
- **AI never decides**: the assistant (LangGraph in `lib/ai/graph.ts`) only answers from `knowledge.ts`, drafts forms the user submits, and orders rule-based suggestions from `context.ts` (links never come from the model). It must not write to the database or be used by matching, expiry, safety or permissions. All LLM calls go through `askStructured()` in `lib/ai/provider.ts`: it tries each configured provider in order and zod-validates the JSON reply, so a busy or wrong provider falls through to the next.
- **Auth is re-checked in the database** by `requireRole()` / `requireUser()` in every page, action and route handler. The proxy is only an optimisation. Actions for a restricted role also check `status === "active"` (verified NGOs and volunteers only).
- Ownership is enforced in the service query itself: `restrictToDonor` / `restrictToNgo` / `restrictToVolunteer`, or `WHERE donor_id = …`. Don't trust IDs coming from the client.
- Contact details are shared only once someone is committed: NGOs see donor phones after a match, and volunteers see donor and NGO phones after accepting. Unverified volunteers never see open tasks.
- Photos are stored as `bytea` and served only through auth-checked route handlers (`…/image`, `…/proof/[step]`) via `imageResponse()`. Max 2 MB; JPG/PNG/WebP (`IMAGE_TYPES`, `MAX_IMAGE_BYTES`).
- Housekeeping: `runHousekeeping()` (expiry + matching + stale volunteer offers + dispatching waiting tasks) runs at most once a minute per process from the signed-in layout, and on demand from `GET /api/cron/housekeeping` (Bearer `CRON_SECRET`). Portal pages also run their own sweeps: `sweepDonorDonations()` (expiry warnings) and `sweepVolunteerTasks()` (pickup reminders).
- **Two kinds of NGO request.** A `food_requests` row is always one NGO ↔ one donation: a direct request (`status` PENDING → donor decides) or a system match (`need_id` set, `status` MATCHED → NGO accepts or SKIPS). A `food_needs` row is the NGO's requirement. Its stage and progress (meals requested/matched/delivered/remaining) are **derived** from its attached rows in `lib/requests/meta.ts`; don't store them. UNIQUE (donation_id, ngo_id) also stops a donation being re-proposed to an NGO that skipped it.
- Matching (`matchOpenNeeds`) proposes at most one waiting match per need, and never offers a donation that is already offered elsewhere. It runs after a donation is posted, after a need is created or edited, after an allocation or cancelled match, on NGO pages, and in housekeeping. All rules and weights live in `lib/matching/meta.ts` (`MATCH_RULES`, `scoreCandidate`): hard filters in SQL, then a deterministic score (expiry 0.4, distance 0.35, quantity 0.25). A proposal asks only for the meals still needed.
- Matching history: a DB trigger on `food_requests` writes `match_events` for every status change; allocation adds an ALLOCATED row. Don't write status-change rows yourself.
- Locations: `lat/lng` on users, donations (`pickup_*`), food_needs and the delivery snapshot are optional; code falls back to the profile pin (`coalesce(...)`), then to area text. Distances are straight-line.
- Live location (`live_locations`, `/api/deliveries/[id]/location`) is opt-in per person, only for the delivery's donor, NGO and volunteer (admins read-only), only while ASSIGNED/PICKED_UP/IN_TRANSIT, and rows are deleted when the task ends (`closeTask`). A volunteer's saved home base is never shown to donors/NGOs; role maps show private homes (individual donors, volunteers) rounded to ~1 km except to admins.
- Admin actions (verify, suspend, edit, cancel, release, offer to volunteer, confirm delivery, record meals) are written to `activity_log` through `recordActivity()` (`lib/admin/log.ts`), as are exports and security events (`login_locked`, `password_change`). `/admin/activity` browses it; every new action needs a label in `ADMIN_ACTION_LABEL`. Status changes go to `donation_events`. Admin edits to donation details must not insert `donation_events` rows, because the timeline assumes one event per status.
- **Admin monitoring** (`lib/admin/monitor.ts`, thresholds in `MONITOR_RULES`): the dashboard's "Needs attention" card lists stuck work (no volunteer, overdue pickup, stalled delivery, meals not recorded, urgent unmatched needs, recent expiries). Resolutions on the admin donation page go through the normal workflow: `adminOfferToVolunteer` (a `task_offers` row, still accepted or declined), `adminConfirmDelivery`, `adminCompleteDonation`.
- **Security (Segment 20):** sessions carry `users.session_version` (`v` in the JWT); the DAL rejects a mismatch. Bump it to sign an account out everywhere (password change, suspend/deactivate). Login is throttled per email (5 / 15 min) and per IP, sign-ups per IP (`lib/rate-limit.ts`, in-memory). Server actions parse forms with `formValues()` (strips control/bidi characters) and guard client ids with `isId()`. Photos go through `readPhoto()` (`lib/uploads.ts`), which checks the real file signature. Machine endpoints use `hasBearerSecret()` (constant time, 16+ chars). Security headers/CSP live in `next.config.ts`; the CSP allows only same-origin scripts/connections and https images (map tiles). Production refuses to seed the admin without `ADMIN_PASSWORD` (unless `DEMO_MODE`).
- User statuses: `pending` (awaiting verification), `active`, `suspended`, `deactivated`. The DAL and login reject the last two. `setUserStatus()` in `lib/admin/service.ts` also releases what a blocked account holds.

### How to add things

- **Schema change:** edit `src/db/schema.ts` **and** append idempotent SQL (`ALTER TABLE … ADD COLUMN IF NOT EXISTS`, `CREATE … IF NOT EXISTS`) under a `-- Segment NN` comment in the `DDL` string in `src/db/index.ts`. The DDL re-runs on every start and on hot reload when the string changes. Never edit earlier DDL in a way that breaks existing local databases.
- **New notification type:** add it to `NOTIFICATION_TYPES` (schema.ts) and to `STYLE` in `src/components/notifications-view.tsx`. The `Record` type forces the second step.
- **New form:** add a zod schema to `validation.ts`, write a server action that returns `FormState` (`{ errors, message, success }`), and build a client form with `useFormAction` (it keeps typed input on validation errors). Pass both `action` and `onSubmit` to `<form>`.
- **New portal page:** put it under `src/app/(app)/<role>/`, call `requireRole(role)` first, and add a nav entry in `NAV` / `PORTAL` in `src/components/layout/app-navbar.tsx`.

## Conventions

- Match the surrounding style: short JSDoc on non-obvious functions, services return `false`/`null` or an error string instead of throwing for business-rule failures, and actions translate that into a `FormState.message`.
- Labels, badge tones and derived stages go in `meta.ts` (safe to import from client components). DB access goes in `service.ts` with `import "server-only"`.
- UI: mobile-first and Tailwind only; don't use `text-ink-400` for text (fails contrast), using the design tokens in `src/app/globals.css` (`brand-*` green, `ink-*` neutrals, `accent-*` saffron, `cream-*` surfaces, `rounded-card`/`rounded-field`, `shadow-card`/`shadow-raised`). Portals have a fixed bottom tab bar on mobile, and `<main>` already reserves space for it.
- Dates: display with `formatDateTime` / `formatRelative` from `src/lib/utils.ts` (app timezone). `datetime-local` inputs are sent with a hidden `tzOffset` and parsed with `parseLocalDateTime`.
- User-facing copy uses curly quotes and apostrophes (“ ” ’), British spelling ("organisation") and plain, friendly sentences.

## Build history

Work has been delivered in numbered segments; the DDL comments in `src/db/index.ts` mark the schema each one added.

- **Foundation** — design system (`components/ui`), public homepage with live impact stats, layouts, error/404/loading states.
- **Authentication** — JWT cookie sessions, the proxy, the DAL, login, per-role self-registration (`SELF_REGISTRATION` in `lib/auth/roles.ts`), profile and password change.
- **Donor portal** — post a donation (with photo), dashboard, list and filters, detail page with tracking timeline, cancellation, notifications, expiry sweep.
- **Segment 05 — NGO module** — NGO registration (pending until an admin verifies it), find food with filters, food requests, donor accepts or declines, NGO request stages, confirm received, mark distributed with meals served, admin NGO verification.
- **Segment 06 — Volunteer module** — volunteer registration (pending until an admin verifies it) and profile. Availability toggle (`users.available`). Dashboard with active tasks, deliveries and meals delivered. New pickups are offered to available volunteers. Task list with Current and Completed sections. Task detail with donor and NGO contacts and map links. Accept → confirm pickup → confirm delivery, each with a timestamp and optional note/photo (`donation_events.photo_data`). Volunteer notifications: new assignment, task accepted, pickup reminder, pickup confirmed, delivery completed. Admin volunteer verification.

- **Segment 07 — Admin module** — dashboard (users, active donations, pending requests, completed deliveries, impact, verification queue, recent activity); user management views with search and filters by role, status, location and date; approve/suspend/deactivate/reactivate with side effects and reasons; donation management (update details, cancel, release volunteer, full history); request management (cancel food requests, withdraw requests and matches); `activity_log`.
- **Segment 08 — Food donation management** — complete lifecycle with a "Created" first step; automatic expiry (throttled housekeeping + cron endpoint); an expiry guard in `transitionInTx`; cancelled/expired food closes its open requests and matches; admin tracking and editing; `donations_expiry_idx`.
- **Segment 09 — Food requests & recipients** — NGO food requests (`food_needs`: food type, quantity, people, area, address, needed-by, notes), system matching by food type, quantity, location and expiry, NGO accept/skip, progress (requested/matched/delivered/remaining), edit or cancel until food is accepted, close when enough, request history and distribution records. Recipients are tracked only as people/meals and service area.

- **Segment 10 — Matching & allocation** — rule-based scoring (`lib/matching`), partial allocation by splitting donations, match status Pending → Matched → Accepted → Allocated, NGO/admin accept/reject/cancel, `match_events` history and the admin Allocations tab.
- **Segment 11 — Pickup & delivery** — delivery task snapshot, nearest-volunteer offers with accept/decline/timeout (`task_offers`), hand-back before pickup, IN_TRANSIT step, delivery status for donor/NGO.
- **Segment 13 — Food safety** — safety rules + window validation, Safe/Expiring soon/Expired badges, admin pause/clear/withdraw, expiry warnings to donor/NGO/volunteer/admin, dashboard safety panel.
- **Segment 14 — Notifications** — categories + filters, read/unread per item, links to donation/request/need, admin alerts inbox, channel preferences, outbox + webhook channel adapters (email/SMS/WhatsApp/Messenger).
- **Segment 15 — AI assistant** — LangGraph agent (classify → answer with RAG / draft donation / draft food request / organise my updates), Gemini/OpenRouter (Claude optional) behind one provider file, conversation history, rate limit, no-AI help mode, form prefill via `?draft=`.
- **Segment 12 — Location & maps** — map pins + LocationPicker, Leaflet maps loaded lazily, distances, Google Maps navigation, opt-in live location, and a `/map` page per role.
- **Segment 16 — Dashboards & analytics** — per-role "over time" card (7 days / 30 days / 90 days / 12 months, CSS bar chart), full-screen assistant with titled chat history (rename/delete).
- **Segment 17 — WhatsApp / Messenger via n8n** — account linking by code, DONATE / NEED / YES / NO / STATUS / STOP by chat, key status updates to linked chats, starter n8n workflow.
- **Segment 19 — Admin monitoring** — "Needs attention" queue, admin resolutions (offer pickup to a chosen volunteer, confirm delivery, record meals served), `/admin/activity` log with filters, safety-window check on admin edits.
- **Segment 20 — Security** — session versioning, login/sign-up rate limits, input sanitising, id guards, file signature checks, security headers/CSP, constant-time bearer checks, no default admin password in production.
- **Segment 21 — Responsive & accessible** — hint text contrast (ink-500 minimum for text), visible focus rings on every input, keyboard-scrollable tables, admin nav in the account menu below `xl`. Main workflow tested at 320–1440 px.
- **Segment 18 — Data & reporting** — admin reports (summary, by month/area/donor type/category) with filters and CSV exports (report, donations, deliveries, requests, users), NGO report page.

### Known gaps (planned before launch)

- No scheduled jobs: expiry and reminders run only when pages load.
- No geocoding: pins are set by GPS or by tapping the map; without pins matching falls back to area text. Routes are straight lines (no routing engine). Map tiles come from the public OpenStreetMap server (set `NEXT_PUBLIC_MAP_TILE_URL` for production).
- Live location is polling (15 s), not push, and only while the sharing page is open.
- WhatsApp only allows free-form messages within 24 h of the user's last message; outside that window n8n must send an approved template (not built). The n8n workflow is a template that hasn't been run against a live account.
- Outside notification channels are webhook adapters; connecting a real provider (e.g. SMTP, Twilio, WhatsApp Cloud API) means implementing it in `lib/notifications/channels.ts`. The assistant rate limit is in-memory per process.
- Matching proposes one donation per need at a time, and a proposal holds that donation (from other needs) until the NGO acts. There is no proposal timeout yet (volunteer offers do time out).
- Admin lists show the latest 100 rows (no pagination yet). Admins are seeded; there's no UI to create another admin.
- Proof photos are visible only to the volunteer (not yet shown to donors or NGOs).
- Rate limits are in-memory per process (move to a shared store with several servers). Photos are stored in Postgres; move them to object storage as volume grows.
- Production (Vercel) needs a hosted Postgres: with `DATABASE_URL` (or `POSTGRES_URL`) set, `src/db/index.ts` uses node-postgres and runs the DDL in one transaction under `pg_advisory_xact_lock`; without it, PGlite. On Vercel without a URL it fails with a clear message (the filesystem is read-only).
